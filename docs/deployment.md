# Развёртывание и интеграция с презентацией

**Статус:** план эксплуатации; команды выполняются только после аудита реального VPS.

## 1. Среда

- Отдельный проект на существующем Ubuntu VPS с публичным IP.
- `bot` и `web` работают разными сервисами systemd с собственным пользователем или ограниченными правами.
- Python в отдельном virtualenv; SQLite-файл в каталоге данных, вне Git.
- Конфигурация через переменные окружения или файл с правами `0600`: `BOT_TOKEN`, `ADMIN_TELEGRAM_ID`, `DATABASE_PATH`, `WEB_HOST`, `WEB_PORT`, `PUBLIC_BASE_URL`.
- Логи отправляются в journald без токенов, приватных идентификаторов и избыточного текста пользовательских сообщений.

**Нельзя** предполагать, что 80/443 свободны, менять настройки уже работающих ботов или публиковать Uvicorn без проверки действующей конфигурации. Сначала инвентаризация VPS: службы, прослушиваемые порты, firewall, reverse proxy, доступность по внешнему IP и резервная копия конфигурации.

## 2. Сетевая схема

```text
Browser -> https://<PUBLIC_IP>/screen -> TLS reverse proxy -> http://127.0.0.1:<PORT> -> FastAPI
Telegram users -> Telegram -> bot on VPS -> SQLite
```

Веб-API и страница результатов — только чтение. FastAPI слушает loopback; наружу опубликован только TLS-прокси. Для публичного IP требуется корректный сертификат и его автоматическое продление. Let's Encrypt с 2026 года поддерживает IP-сертификаты короткого срока действия, но конкретную связку ACME-клиента и прокси нужно **отдельно проверить**. Не полагаться на сертификат, выдаваемый для доменного имени, при подключении по IP.

Если HTTPS по IP окажется недоступен в срок, допустим временный безопасный публичный URL через согласованный туннель или внешний прокси (только после отдельного решения). Не публиковать административные действия без аутентификации.

## 3. Последовательность внедрения

1. Локально проверить бота и SQLite на тестовых аккаунтах.
2. Поднять FastAPI только на loopback; проверить JSON и SSE.
3. Упаковать frontend локально без обязательных CDN.
4. Настроить процессы systemd с автоперезапуском, `WorkingDirectory`, секретами в environment file и правами доступа к БД.
5. Проверить публичный доступ к `/screen` и `/api/results` **с внешней сети**.
6. Проверить сертификат, TLS, reconnect SSE, firewall и восстановление после reboot.
7. Провести полную репетицию с QR-кодом и PowerPoint.
8. Создать чистую сессию для выступления (данные тестовых раундов остаются отдельно).

## 4. PowerPoint и демонстрация

### Базовый способ (надёжный)

На стартовом слайде — QR-код Telegram deep link. Рядом может быть кнопка/гиперссылка на `https://<PUBLIC_IP>/screen`.

На компьютере с презентацией открыть адрес результатов в браузере, развернуть на полный экран, затем вернуться в PowerPoint. Telegram на компьютере не нужен: все ответы обрабатывает VPS. Но **Telegram должен быть доступен самим участникам**.

### Резервный вариант: Windows Internet Shortcut

Создать рядом с PPTX файл `Результаты голосования.url`:

```ini
[InternetShortcut]
URL=https://<PUBLIC_IP>/screen
```

Адрес — шаблон; заменить после публикации. Ярлык запускается браузером и не требует надстройки PowerPoint.

### Экспериментальный вариант: веб-страница внутри слайда

Только после проверки версии Office и политики установки надстроек на **том самом** компьютере, где будет семинар. Плагины и встроенный webview не являются обязательной частью MVP. Не ставить успешность выступления в зависимость от них.

## 5. Устойчивость во время семинара

- На странице показывать время последнего обновления и статус соединения.
- При обрыве сети не сбрасывать диаграмму: показывать последние данные и надпись о недоступности обновлений.
- Подготовить статичный резервный слайд на случай недоступности VPS или браузера.
- Проверить, открывается ли Telegram у студентов **из доступных им сетей**; если нет, решение о резервном веб-голосовании принять до мероприятия.
- Административные действия не должны зависеть от университетского компьютера: используются с личного устройства ведущего.

## 6. Безопасность и обслуживание

- Не коммитить `.env`, токен бота, IP сервера вместе с доступами, SSH-ключи, дампы с Telegram ID или реальную SQLite-базу.
- Хранить минимум личных данных; результаты публично только агрегированные.
- Использовать ограничения доступа, таймауты и разумный лимит публичных SSE-подключений.
- Регулярно проверять состояние bot/web и свободное место на диске.
- После мероприятия сохранить обезличенные итоги и решить срок удаления личных идентификаторов, тестовых голосов и журнальных данных.

## 7. Ещё требуется уточнить

- Фактический IP, ОС VPS, занятость портов, способ TLS.
- Имеющиеся systemd-службы и reverse proxy; ничего не заменять без проверки.
- Проверенная версия PowerPoint и доступность публичного адреса из аудитории.
- Наличие доступа участников к Telegram или необходимость браузерной альтернативы.
