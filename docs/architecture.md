# Архитектура и контракты

**Статус:** проектная схема, реализация не начата.

## 1. Контекст и компоненты

```text
              Telegram clients
                     |
                Telegram API
                     |
            [bot / aiogram 3]
                     |
                  SQLite
                     |
            [web / FastAPI] ---> GET /health
                  /    \
         REST snapshots  SSE events
                 \       /
              [browser page]
                 Chart.js
                     |
                  Projector
```

**Бот** обрабатывает действия пользователей и администратора, записывает голоса, меняет статус сессии и запускает отправку итогов.  
**API** предоставляет только публичные агрегированные состояния и статическую страницу.  
**Frontend** отображает статистику и получает события обновления; не хранит секреты.  
**БД** — единственный источник истины. Перезапуск процесса не должен обнулять результаты.

Рекомендуемый вариант первой версии: **два независимых процесса** под systemd, совместно использующих SQLite на одном VPS. Не размещать базу на сетевой файловой системе. Включить WAL и `busy_timeout` для конкурентных транзакций.

## 2. Модель данных (логическая)

### `poll_sessions`

| Поле | Тип / смысл |
|---|---|
| `id` | первичный ключ |
| `status` | `WAITING`, `OPEN`, `CLOSED` |
| `created_at` | UTC timestamp |
| `started_at` | UTC timestamp, nullable |
| `closed_at` | UTC timestamp, nullable |
| `version` | монотонная версия публичного состояния |

Обеспечить инвариант **не более одной `OPEN` сессии**, желательно ограничением БД плюс проверкой в транзакции. Увеличивать `version` при изменении голоса или состояния.

### `votes`

| Поле | Тип / смысл |
|---|---|
| `id` | первичный ключ |
| `session_id` | FK на `poll_sessions` |
| `telegram_user_id` | числовой идентификатор; не отдавать в API |
| `choice` | `ios`, `android`, `other` |
| `created_at` / `updated_at` | UTC timestamps |

Уникальное ограничение: `UNIQUE(session_id, telegram_user_id)`. Изменение голоса — транзакционный UPSERT; не считать повторный выбор новым голосом.

### `notification_deliveries` (для рассылки итогов)

Минимальный журнал доставки по `(session_id, telegram_user_id, type)`: `pending/sent/failed`, время последней попытки. Не запускать параллельные рассылки итогов при повторном нажатии администратора. Учитывать Telegram flood limits и ошибки отправки; гарантия ровно одного уведомления в условиях сетевого обрыва недостижима без поддержки идемпотентности на стороне Telegram.

## 3. Публичные маршруты

| Метод | Путь | Ответ |
|---|---|---|
| GET | `/screen` | полноэкранный интерфейс |
| GET | `/api/poll` | текущая сессия и статус |
| GET | `/api/results` | агрегированная статистика |
| GET | `/api/events` | SSE с актуальными обновлениями |
| GET | `/health` | минимальная проверка процесса |

Никаких публичных `POST /start`, `POST /close`, `POST /vote`; запись происходит только через проверенные Telegram-обработчики. В дальнейшем веб-голосование потребует **отдельного** продуманного контракта безопасности.

### Пример `GET /api/results`

```json
{
  "session_id": 3,
  "status": "OPEN",
  "version": 42,
  "total": 30,
  "results": {
    "ios": {"votes": 12, "percentage": 40.0},
    "android": {"votes": 17, "percentage": 56.7},
    "other": {"votes": 1, "percentage": 3.3}
  }
}
```

Числа здесь **демонстрационные**. Если нет сессии, API возвращает явно описанное состояние (например, `session_id: null`, `status: "NONE"`, нулевые значения), а не 500.

Проценты вычисляются от общего количества голосов и могут давать суммарно 99.9 или 100.1 из-за округления до одного знака.

## 4. Обновления в реальном времени

1. Клиент загружает `/api/results` и отрисовывает начальный snapshot.
2. Затем подключается к `/api/events` через `EventSource`.
3. API наблюдает версию состояния в БД и при изменении отправляет **полный агрегированный snapshot** (например, событие `results_updated`).
4. При закрытии — отдельное событие `poll_closed` или snapshot со статусом `CLOSED`.
5. При потере связи клиент отображает последнюю статистику со статусом «Нет соединения» и автоматически переподключается; после reconnect сервер присылает свежий snapshot.

Для MVP достаточно периодически проверять версию БД внутри SSE-обработчика; не нужен Redis или внешний message broker. Добавить heartbeat, отключение stream по закрытию клиента, лимиты подключений и простой REST fallback (периодический GET), если SSE недоступен из конкретной сети.

**Не создавать по соединению бесконечно работающий поток без проверки `request.is_disconnected()`**, иначе возможна утечка ресурсов.

## 5. Механика голосования

- При `/start` бот объясняет цель голосования и обработку Telegram ID.
- Участник может голосовать только при `OPEN`; действия через устаревшие callback-кнопки проверяются **по текущему состоянию БД**.
- Изменение ответа атомарно заменяет прежний голос.
- Кнопки администратора требуют проверки user ID на каждый вызов и подтверждения закрытия.
- `CLOSED` неизменяем; новый раунд — новая сессия.
- Результаты одной сессии не попадают в другие.
- Закрытие сессии и постановка уведомлений в очередь происходят согласованно.

## 6. Визуализация

- Категории iOS/Android — два крупных вертикальных столбца.
- «Другая ОС» — отдельная числовая подпись, чтобы проценты не вводили в заблуждение.
- Общая ось Y; шкала начинается от 0 и не должна сокращаться во время показа (увеличивать максимум при необходимости).
- Анимация сглаживает изменения, но цифры всегда отражают полученный snapshot.
- Учитывать состояния ожидания, активного голосования, закрытия и отсутствия сети.
- Критичные JS/CSS-ресурсы лучше обслуживать самим VPS, чтобы сторонний CDN не стал дополнительной точкой отказа во время выступления.
